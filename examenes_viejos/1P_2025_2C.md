## 6. Supongamos una colección 'orders' en una instancia de MongoDB. Calcular el total vendido por product usando la estrategia Map-Reduce.

```javascript
{ "_id": 1, "product": "laptop",   "quantity": 2, "price": 1000 }
{ "_id": 2, "product": "mouse",    "quantity": 5, "price": 50 }
{ "_id": 3, "product": "laptop",   "quantity": 1, "price": 1000 }
{ "_id": 4, "product": "keyboard", "quantity": 3, "price": 80 }
```

> [!question]- Respuesta
> _Resolución propia: el PDF no trae la respuesta de las preguntas a desarrollar._
>
> `map` emite por cada orden la clave `product` y el importe `quantity * price`; `reduce` suma los importes de cada clave.
>
> ```javascript
> db.orders.mapReduce(
>   function () { emit(this.product, this.quantity * this.price); },
>   function (key, values) { return Array.sum(values); },
>   { out: "total_por_producto" }
> );
> db.total_por_producto.find();
> ```
>
> Resultado:
>
> - **laptop**: 2·1000 + 1·1000 = 3000
> - **mouse**: 5·50 = 250
> - **keyboard**: 3·80 = 240
>
> Si "total vendido" se interpreta como unidades, se emite `this.quantity`: laptop 3, mouse 5, keyboard 3.

## 15. Interprete y explique con sus palabras qué hace la siguiente query de MongoDB:

```javascript
db.orders.aggregate([
  { $match: { payment_method: "cash" } },
  { $group: { _id: "$order_date", totalQuantity: { $sum: "$quantity" } } }
])
```

> [!question]- Respuesta
> _Resolución propia: el PDF no trae la respuesta de las preguntas a desarrollar._
>
> Es un pipeline de agregación de dos etapas:
>
> - **$match**: se queda solo con las órdenes pagadas en efectivo (`payment_method = "cash"`). Es el WHERE.
> - **$group**: agrupa esas órdenes por `order_date` y suma `quantity` en el campo `totalQuantity`. Es el GROUP BY con SUM.
>
> Devuelve un documento por fecha, `{ _id: <fecha>, totalQuantity: <total> }`, con la cantidad total de unidades vendidas en efectivo cada día. En SQL:
>
> ```sql
> SELECT order_date, SUM(quantity) AS totalQuantity
> FROM orders WHERE payment_method = 'cash'
> GROUP BY order_date;
> ```

## 16. Considerando el siguiente esquema de BD, provea una consulta en MySQL que devuelva una lista con los datos de aquellas obras en ejecución junto con una columna denominada "Resp_obra" donde figure el arquitecto o ingeniero responsable de la obra, según sea su tipo.

![[bd2-parcial-2025-esquema-obras.png|650]]

## 29. Explique cómo se constituye una Primary Key en Cassandra y qué función cumple cada componente. Incluya ejemplos en su explicación.

> [!question]- Respuesta
> _Resolución propia: el PDF no trae la respuesta de las preguntas a desarrollar._
>
> La primary key tiene dos partes y el orden importa:
>
> - **Partition key**: el primer componente. Se hashea para obtener el token que decide en qué nodo se guarda la fila. Las filas con la misma partition key quedan juntas en la misma partición. Puede ser compuesta, con paréntesis extra.
> - **Clustering key**: el resto de los componentes. Define el orden físico de las filas dentro de la partición, y por eso solo se puede hacer ORDER BY sobre ella.
>
> Ejemplos:
>
> - `PRIMARY KEY (idusuario)`: partition key idusuario, sin clustering key; cada partición tiene una sola fila.
> - `PRIMARY KEY (mes, nombre)`: partition key mes, clustering key nombre; todas las filas de un mes juntas, ordenadas por nombre.
> - `PRIMARY KEY ((idusuario, mes), nombre, registro)`: partition key compuesta; en el WHERE hay que dar idusuario y mes.
>
> _Ver [[8_Cassandra#Clave primaria: partition key y clustering key]]._

## 31. Explique las ventajas y desventajas de implementar un modelo embebido vs. no hacerlo en MongoDB.

> [!question]- Respuesta
> _Resolución propia: el PDF no trae la respuesta de las preguntas a desarrollar._
>
> **Embebido** (subdocumentos dentro del mismo documento):
>
> - Ventajas: se lee todo en una sola consulta, sin `$lookup`, y la escritura de un documento es atómica.
> - Desventajas: duplica datos si lo embebido se comparte (hay que actualizarlo en todos lados), el documento puede crecer sin límite y tiene un tope de 16 MB.
>
> **Normalizado** (referencias por `_id`):
>
> - Ventajas: no duplica, sirve para many-to-many y jerarquías grandes, los documentos quedan chicos.
> - Desventajas: hacen falta varias consultas o `$lookup`, y actualizar varios documentos no es atómico.
>
> Conviene embeber en relaciones "contiene", one-to-one u one-to-few que se leen juntas.
>

## 32. Dada la siguiente secuencia de cesión, revocación de privilegios y operaciones en SQL estándar, decir cuáles son los privilegios y sobre qué objetos los conservan U0, U1, U2 y U3 al final. Nota: U0 es admin; Cliente es una tabla; CS: ClienteSub-30, CSV: ClienteSub-30Vip, ambos son vistas.

```sql
U0: GRANT SELECT ON CS, CSV TO U1;
U0: GRANT INSERT, UPDATE ON CLIENTE TO U1 WITH GRANT OPTION;
U0: UPDATE CS SET Tipo = "Vip" WHERE Nombre = "Esteban Gonzalez";
U0: GRANT SELECT ON CLIENTE TO U1, U2 WITH GRANT OPTION;
U1: GRANT SELECT ON CLIENTE TO U3 WITH GRANT OPTION;
U3: GRANT SELECT ON CLIENTE TO U2;
U0: GRANT SELECT ON CSV TO U2;
U1: REVOKE SELECT ON CLIENTE FROM U3 CASCADE;
```

> [!question]- Respuesta
> _Resolución propia: el PDF no trae la respuesta de las preguntas a desarrollar._
>
> - **U0**: todos los privilegios sobre todo (es admin). El UPDATE sobre CS es una operación, no cambia privilegios.
> - **U1**: SELECT sobre CS y CSV; INSERT, UPDATE y SELECT sobre Cliente, los tres WITH GRANT OPTION.
> - **U2**: SELECT sobre Cliente WITH GRANT OPTION (el que le dio U0) y SELECT sobre CSV.
> - **U3**: nada.
>
> El REVOKE CASCADE le saca a U3 el SELECT sobre Cliente y arrastra el que U3 le había dado a U2. Pero U2 conserva el SELECT que le dio U0 directamente.
